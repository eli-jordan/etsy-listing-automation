What exists now

Deployment · synchronous stage order
Render→Printify product→Publish draft→Etsy listing→Images→Videos

CLI and the FIFO UI deployment worker call the same engine. Lifecycle handling selects retract/retire/resume paths. Successful stages fold and record progress; remote IDs advance to later stages. The UI plan resource separately renders full-size previews for promotion during apply.

Batch creation and AI · separate from deployment
Frozen listing template + uploads→Staging + confirm→Ordinary listings→Batch AI queue
Optional brief→Buyer queries→Market evidence→Durable proposal→Seller acceptance

Codex → Claude → Grok is the default provider availability fallback chain. Per-run AI threads are distinct from deployment. UI deployment cancels and waits for AI on its listing names; CLI intentionally does not coordinate with that queue.

Process-local: run registries, write locks, decoded-image cache and worker queues. Durable: workspace documents, lockfiles, rendered/preview bytes, market/proposal caches, staging and batch records. Concurrent CLI/UI writes and shared registries across multiple ASGI workers are not coordinated.

HighViolationImplementedF01

Reviewed apply can accept changed render inputs

engine/run.py:141engine/stages/render.py:584ADR-0039

The review digest hashes Plan presentation fields and drops snapshots. Render actions contain paths and generic reasons, but no design, template, photo or recipe digest. Different input bytes can therefore produce the same fingerprint.

Reproduced

In a temporary synthetic fixture, plan with RenderStage, change one RGBA design pixel, then plan again. Desired design hashes differed, fingerprints matched, and apply_listings accepted the original fingerprint and rendered the changed design. This covers the render-only pipeline; another stage may detect a particular edit in a configured shop, but that does not repair the render review contract.

Consequence

A seller can apply pixels that were absent from the reviewed render. ADR-0039’s guard is weaker than its promise to reject file edits after review.

Potential solution Strong

Add stable review-input digests alongside existing changes and drift, including per-scene content/recipe evidence. Continue excluding transient preview flags and CDN URLs. Amend ADR-0039 explicitly before implementation because it currently specifies the serialized Plan without snapshots.

Validation for a future repair

Reject an old fingerprint after design/photo bytes or geometry change while paths and generic work reasons remain identical. Retain acceptance after preview completion and rejection after remote drift.

HighViolationF02

Layout accessors allow symlink targets outside the workspace

workspace/workspace.py:429,867,925ui/api/templates.py:569ADR-0013

resolve() checks resolved containment for file references, but many layout accessors only join validated name segments. A valid segment can still name a directory symlink or Windows junction pointing outside the root.

Reproduced

A temporary mockup-templates/escape symlink pointed at a sibling directory. scene_photo("escape", "ivory").path resolved outside the workspace without refusal. Listing-media serving already uses a stronger resolved-owner check.

Consequence

Template readers and writers can follow existing filesystem links outside their intended roots. Creating the link requires filesystem access; this is a containment gap, not a demonstrated remote link-creation exploit.

Potential solution Strong

Centralize resolved-root checks for layout paths, including nonexistent write targets with linked parents. Cover listing/template/cache accessors and enumeration, while retaining stricter owner-root checks for media serving.

Validation for a future repair

Test directory/file symlinks and Windows junctions for reads, writes, enumeration and deletion. Exercise HTTP template routes with escaping targets and check actionable refusals.

HighViolationImplementedF03

Local render refusals escape the engine error vocabulary

engine/stages/render.py:113,507engine/stages/placement.py:30engine/run.py:364test_render_stage.py:83

TemplateNotFoundError/TemplateAssetError inherit FileNotFoundError; MediaColourMismatchError/ArtworkResolutionError inherit ValueError. Desired-state resolution raises them instead of returning Blocked. The run loop catches only UserFacingError.

Reproduced

Replacing a fixture’s template reference with missing-template made plan_listings raise TemplateNotFoundError instead of returning a blocked stage or failed-listing outcome. An existing behavior test explicitly expects that exception from build_plan.

Consequence

A local configuration mistake can terminate a CLI --all batch. The UI executor catches it as an internal error rather than showing the intended per-stage refusal.

Potential solution Strong

Move local predicates/messages into shared validation checks and adapt them to Blocked in desired(). Loading failures that must remain exceptional should be actionable UserFacingError values so the batch continues; that fallback does not replace stage-level refusal reporting.

Validation for a future repair

Plan a bad template/artwork reference followed by a valid listing. Show the bad stage’s message, preserve later stage plans and continue to the valid listing.

MediumViolationF04

The supposedly pure listing check opens design images

config/listing_validation.py:137,155workspace/facts.py:72engine/stages/gates.py:63

check_listing() reaches check_design_resolution(), which stats a Path and calls Pillow Image.open. WorkspaceFacts caches profiles, templates and video facts, but not image dimensions/mode or image-read failures.

Confirmed in source

The same path-opening check serves both the editor aggregate and product-stage gate. The previous “check_listing is pure” statement was inaccurate.

Consequence

Repeated checks reopen shared designs and depend on filesystem state. Request-fact ownership and no-I/O validation remain incomplete.

Potential solution Strong

Gather immutable design dimensions, mode and read failures through WorkspaceFacts. Pass those facts to the shared config predicate and retain the stage gate adapter.

Validation for a future repair

Test checks from facts with file access forbidden; separately test loading and one probe per shared design per request.

MediumViolationImplementedF05

Workspace layout and stage knowledge leak into callers

engine/stages/render.py:762ui/api/templates.py:190ui/api/media_files.py:62ui/api/listings.py:199,210ADR-0038

RenderStage._prune_previews walks template subdirectories and globs PNGs. HTTP serializers rebuild workspace paths with layout constants. UI listing status reads remote keys and decodes AppliedEtsyListing to infer lifecycle.

Confirmed in source

Enumeration/path construction occur outside workspace, and the HTTP adapter interprets stage persistence. Read-only Lockfile access itself uses an exported engine type and is distinguished from a second deployment walk.

Consequence

Layout changes require edits in several packages. UI status knows stage-specific storage despite the stage-facts principle.

Potential solution Strong

Move preview enumeration/pruning and relative-path serialization into workspace. Expose an engine status/remote-summary operation for stage-owned interpretation; keep HTTP formatting in UI.

Validation for a future repair

Behavior tests should cover pruning; contract tests should cover real photo/media paths and lifecycle summaries. Distinguish generic cache adapters and pre-workspace setup from layout leaks.

MediumViolationF06

Setup still builds an Etsy client outside connections

setupcmd/interactive.py:204connections.py:180

_default_etsy_access resolves the key, loads tokens, chooses a bearer, builds EtsyTransport and wraps HttpEtsyShopClient. connections.etsy_shop_client repeats that assembly.

Confirmed in source

Both currently attach an optional bearer only when stored tokens exist. They agree today, but independently implement the policy that connections should own.

Consequence

Refresh/auth changes can diverge between setup and ordinary client wiring.

Potential solution Strong

Have connections provide the shop client and stored owner-id fact setup needs. Preserve injected factories and shop access before sign-in.

Validation for a future repair

Drive setup through the production wiring with a fake transport for missing tokens, present tokens and refresh failures.

MediumDependency riskImplementedF07

Config depends upward on market and forms a package cycle

config/settings.py:33market/__init__.py:31market/cache.py:42workspace/workspace.py:33

config.settings imports market.models.MarketWeights. Market cache/snapshot import workspace; workspace imports config.settings. Importing market.models also executes a package initializer exporting research/client-facing code.

Confirmed dependency graph

config → market → workspace → config. Current imports/tests work; this is package coupling, not a reproduced import failure. The root’s strictly-downward claim is stale.

Consequence

A foundational settings type pulls in research/client initialization and makes future imports sensitive to ordering.

Potential solution Worth exploring

Move scoring-weight configuration/value types into config or a small neutral domain-model module, then let market consume them. Avoid extra services solely to redraw arrows.

MediumDependency riskF08

Numerical rendering relies on an undeclared direct dependency

pyproject.toml:14render/passes.py:16render/maps.py:16uv.lock:658

NumPy is directly imported throughout rendering and preview caching but is not declared by the project; OpenCV supplies it transitively. The lock resolves NumPy 2.5.2. Starlette, prompt_toolkit and pydantic-core are also directly imported through parent dependencies.

Manifest/import comparison

No missing import was observed. NumPy is the material case because floating-point numerical operations participate in the deterministic pixel contract.

Consequence

A fresh resolution or installation outside the repository lock can change a numerical rendering dependency without an explicit project decision. No pixel change from a NumPy upgrade was demonstrated.

Potential solution Strong

Declare NumPy directly with a tested compatibility/pinning policy. Review other transitive imports for explicit declarations; pydantic-core must stay compatible with pydantic. Preserve exact OpenCV/Pillow pins and validate goldens before numerical bumps.

Validation for a future repair

Install from declared metadata and run render goldens on Windows/Linux with the intended resolution.

MediumDependency riskImplementedF09

The build hook can ship a stale SPA

hatch_build.py:24,38pyproject.toml:44ci.yml:63

The hook treats any existing dist directory as current. When absent it uses npm install rather than npm ci. CI builds first from its lock; a local wheel can reuse older frontend source/API assets.

Confirmed in source

The early return has no source-freshness check. No stale production wheel was built during this audit.

Consequence

The packaged backend and SPA can disagree even when source documents and generated contracts are in sync.

Potential solution Strong

Build release assets explicitly from package-lock.json after contract generation/checking. Rebuild for release or verify a source/build stamp before reusing dist. Retain a documented Python-only installation path.

Validation for a future repair

Change frontend source/schema after an initial build, package again and inspect wheel assets or a build stamp; also test a clean locked build.

HighPolicy gapImplementedF10

Hermetic CI selects real-API E2E tests

ci.yml:93pyproject.toml:84

The Python job passes -m "not browser". pytest’s command-line marker replaces addopts’ -m "not e2e" rather than combining with it.

Confirmed by collection only

The exact CI marker selected 2648 of 2745 tests, including tests/e2e/test_ai_run_e2e.py and real publish/deploy tests. No test body ran. Credential guards may skip execution; the selection itself is not hermetic.

Consequence

With matching credentials/workspace environment, the PR job can perform real shop operations. On a clean runner, it still violates the documented layer separation.

Potential solution Strong

Use -m "not browser and not e2e" in the hermetic job. Keep the separate E2E workflow explicit and update adjacent comments/guidance together.

Validation for a future repair

Collect with each workflow’s exact expression and assert that PR selection contains no e2e-marked tests while the dedicated job selects them.

MediumViolationImplementedF13

Etsy app keys are read eagerly despite the lazy invariant

connections.py:133,151,197test_connections.py:62

Etsy transport/shop/market factories call etsy_app_key during construction, immediately reading Secrets.load. Bearers and Printify tokens remain lazy; optional-client absence is determined eagerly.

Confirmed call graph and tests

A workspace without keys still works. The violation is eager reading against the stated invariant, not a claim that construction always demands credentials.

Consequence

Construction depends on environment/file parsing before a requested operation uses Etsy. The previous blanket lazy claim concealed the exception.

Potential solution Worth exploring

Use a lazy app-key source, or explicitly amend the design contract to allow a non-demanding construction-time availability read. Preserve actionable missing-key/sign-in states. The updated architecture records this exception while retaining the intended rule.

Validation for a future repair

Assert credential-file reads at construction and first request; test malformed/missing credentials without unrelated Etsy work.

MediumDependency riskF14

Renderer changes do not invalidate existing caches

engine/stages/render.py:280,825,878ADR-0012

Input/scene hashes include input bytes and recipes but no renderer-algorithm revision. Unchanged-input outputs can survive code/library changes, and apply can promote a preview made by the prior renderer.

Confirmed payload and promotion logic

Exact OpenCV/Pillow pins exist and are unchanged. No upgrade was performed, and no claim is made that every upgrade changes pixels. The previous two-hash explanation overstated the library-upgrade guarantee.

Consequence

Output hashes notice changed bytes only after bytes are regenerated; they cannot force a re-render by themselves.

Potential solution Strong

Add a deterministic renderer revision to input/scene recipes, or require cache migration for renderer changes. A recipe revision differs from volatile tool_version. Document the chosen policy in ADR-0012 before implementing it.

Validation for a future repair

With identical inputs, change the renderer revision and require fresh outputs plus rejection of old previews. Verify media reupload when the new bytes differ.

Confirmed duplicate rule
